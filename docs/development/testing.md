# Проверки и критерии приёмки

## Уровни доказательства

1. Формат/валидация: JVM/Python unit tests.
2. Конфигурация: `check-config` **того бинарника**, который будет в APK.
3. Локальный transport loopback: обе стороны на контролируемом стенде.
4. Android TUN: запрос из отдельного приложения через реальный VPN, а не только localhost SOCKS.
5. Реальный сервер, сеть, переключения и долгий сон/нагрузка.

Успех уровня 1 не заменяет уровни 2–5. Блокировки узла/сети и изменения браузерного DoH фиксируйте отдельно. В отчёте должны быть пропущенные/непройденные сценарии, а не только успешные.

## Минимальная автоматическая регрессия

- Android: `:app:testDebugUnitTest`, `:app:lintRelease`, `:app:assembleRelease` с `tools/synthetic-tests.init.gradle`.
- Python Builder: `test_core`, `test_policy`, `test_geo`, `test_routing_sources`, `test_dns_pools`; GUI отдельными процессами; frozen EXE self-test.
- `tools/check_removed_protocols.py <apk>`: запрет возвращения удалённых реализаций.
- `tools/check_r8_models.py`: отражение/Gson после R8.
- `tools/check_native_contract.py --go <path>`: контракт Xray с созданным routing overlay.
- `tools/check_vless_import_native.py`, `check_core_fixtures.py`, `check_network_fixtures.py`, `check_release_xhttp.py`: проверьте аргументы `--help` перед запуском; отдельные проверки требуют подготовленных native fixtures.
- Native build-скрипты запускают собственные unit/loopback tests. Их сбой нельзя игнорировать после успешного Gradle.
- `python scripts/check_public_tree.py`: файлы/ссылки и базовые publication guards; не является полным secret scanner.

## Ручная матрица

Основные реально доступные профили: VLESS, Snell, Mieru, NaiveProxy; остальные — только при наличии поддерживаемого рабочего сервера. Один профиль, пары одного протокола и смешанная группа проверяются отдельно.

| Блок | Проверка | Что сохранить |
| --- | --- | --- |
| Импорт | ссылка/файл/подписка, длинный encryption, XHTTP extra, повторное обновление | причины отказа и round-trip без рабочих ключей |
| DNS | один DNS, 8-member pool, auto/priority, отказ, A/AAAA, DoH без IP | эффективная политика, маршрут, уникальный тестовый домен, трассировка |
| DNS-границы | remote не выходит напрямую; browser DoH отдельно; raw JSON отдельно | конфигурация и независимый сетевой сигнал |
| URL-test | удача/отказ/восстановление, подтверждение, удержание, сон | времена тестов/переключений и новые запросы |
| Lifecycle | отмена запуска, повторное соединение, остановка, завершение дочернего ядра | отсутствие зависшего recovery/WakeLock |
| Хранилище | длительная диагностика, ротация, повторный экспорт, очистка cache | размер по категориям до/после без удаления профилей |
| Обновление | установка поверх предыдущего APK той же подписи | package/version/signature, сохранность профилей/настроек |

Во время удалённой беспроводной отладки не выключайте Wi-Fi и не ломайте единственный канал доступа. Смена Wi-Fi ↔ mobile требует отдельного разрешённого стенда. Не меняйте серверные балансировщики ради клиентского теста.

## Энергопотребление

Сопоставляйте одну нагрузку, качество/яркость, сеть, устройство, протокол/группу, зарядку и длительность. Храните заряд и время, CPU процесса и дочерних ядер, байты интерфейса, wakelocks и события переключений. Процент заряда — грубая оценка, не прямая энергия; различный полезный трафик нельзя считать равной нагрузкой без пояснения.

Для A/B используйте несколько повторов и медиану; укажите погрешность и аварийные остановки видео. Не экстраполируйте планшет на другой телефон как измеренный результат. Не опрашивайте ADB каждую секунду в sleep-тесте. Записывайте локально с ограничением объёма; отключение питания вручную не заменяется `dumpsys battery unplug`.

Старые частные тесты не публикуются вместе с личными логами. В 1.5 публикационная проверка не включает повторный многочасовой battery/TUN тест: это явно отражается в отчёте релиза.
