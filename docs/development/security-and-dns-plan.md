Цель — закрыть замечания issues 1–4 проверяемыми изменениями, устранить расхождение сведений о DNS и добавить настраиваемый аварийный DNS и bootstrap в Android и Routing Builder. Дополнительное требование владельца — новый релизный ключ подписи с обновлением поверх старой версии через проверенную ротацию. План не является отчётом о готовности. Изменения не должны удалять профили, подписки и личные правила; package ID и цепочка доверия обновления сохраняются.

## Исправление отображения DNS

На предоставленных снимках маршрутизация содержит шесть удалённых DoH и два прямых DoH, а сведения показывают legacy список `8.8.8.8,1.1.1.1`. В исходном `ConnectionDetails.kt` DNS читается только из `splitDnsJson`; при DNS внутри правил подписки это поле может быть пустым. Второй экран читает также `happRoutingSource`. Эти два пути нужно свести к общему вычислению по тем же правилам приоритета, что у компилятора. Отдельно сохранить полный объект при компиляции наследуемой подписки: без этого исправление экрана будет лишь косметическим.

1. Регрессионный тест воспроизводит 6/2 с пустым `splitDnsJson` и DNS внутри подписки. Отдельные случаи: явный override, отключённое разделение, legacy настройки, некорректный источник.
2. Сведения показывают все DNS группы, а не только первый элемент или legacy поле. Различаются сохранённые настройки, снимок действующей сессии и последний фактически ответивший DNS.
3. Изменения, ещё не применённые к соединению, помечаются явно. Старые события процесса не обновляют новую сессию.
4. Пустой bootstrap нельзя подписывать «системный», пока конкретная цепочка использует иной default. Для raw Xray JSON показывается отдельное управление профилем.
5. DNS имена и частные URL скрываются режимом приватности; URL с токенами не попадают в служебные журналы.

Отсутствие Google на IPLeak само по себе не доказывает ошибку: частный DoH может использовать другой upstream, а автоматический пул не обязан использовать каждого участника. Для проверки выбирается один контролируемый DNS, выполняется запрос из отдельного Android приложения через TUN и сопоставляется с трассировкой/журналом резолвера. Затем повторяются 6/2, авто и приоритетный режим. Собственный DoH браузера и Android Private DNS учитываются отдельно; серверные балансировщики не меняются.

## Семантика системного DNS и аварийного резерва

«Localhost» в пользовательском выборе означает системный резолвер текущей физической сети Android. Это не UDP `127.0.0.1:53`, не MAPDNS TUN и не DNS VPN сервера. Если Android использует Private DNS, системный резолвер может отличаться от DNS провайдера; интерфейс не должен обещать обратное.

Для каждой группы нужен отдельный аварийный резерв: `system`, `resolver` или `disabled`. Он не включается в обычные 1–8 участников пула. При выборе system для удалённой группы имена выходят напрямую: это запрошенное исключение из прежней изоляции DNS, которое отражается в настройках и текущем состоянии.

Алгоритм:

1. Запрос обслуживает основная группа согласно auto/priority и состоянию участников.
2. Аварийный резерв используется только после исчерпания доступных основных участников из-за сетевых/серверных ошибок. NXDOMAIN и корректный пустой ответ не запускают обход фильтрации через резерв.
3. Резерв не участвует в фоновых пробах и не становится предпочтительным участником auto. Часть общего ограничения времени выделяется ему заранее; время не умножается на число серверов.
4. Отмена запроса или старой сессии запрещает последующий резервный запрос. При недоступности самой сети выдаётся понятная ошибка, без бесконечных попыток.
5. Восстановившийся основной пул возвращается в работу с ограниченными проверками и без постоянного опроса.
6. Наблюдения различают обычный ответ, переключение внутри группы и аварийный системный/ручной резерв с фактическим маршрутом.

Для новых конфигураций по запросу владельца default — system. Существующие документы без полей требуют явной миграции: для DNS действующей подписки отсутствие настройки означает default system новой версии; явный disabled сохраняет строгий режим. Общие неподписочные настройки и пользовательские overrides не переписываются автоматически. Изменение default описывается в выпуске; старые клиенты не должны молча проглатывать неизвестные поля.

## Bootstrap и контракт ссылки

Bootstrap отвечает только за начальное разрешение VPN сервера и имён DNS endpoints. Он не заменяет DNS сайтов. IP pin конкретного DoH и статические hosts сохраняют приоритет; TLS hostname, SNI и проверка сертификата остаются неизменными.

Проект расширения внутри `dns` ссылки `tuna://routing/v1`:

```json
{
  "remoteEmergency": {"mode": "system"},
  "domesticEmergency": {"mode": "resolver", "resolver": {
    "transport": "DOH", "endpoint": "https://dns.google/dns-query",
    "bootstrapIp": null, "route": "DIRECT"
  }},
  "bootstrap": {"mode": "system"}
}
```

Это дополнение к существующим pools, selection modes и timeout, не полный импортируемый документ. Ручной remoteEmergency использует VPN; ручной domesticEmergency — DIRECT. System всегда означает физическую сеть напрямую. Для отключения резерва — mode disabled. Для bootstrap: system, наследование общего параметра при отсутствии поля либо явно заданный поддерживаемый резолвер. Доменный bootstrap не должен зависеть от самого себя; в первой реализации ручной общий bootstrap сохраняет существующий формат TCP с literal IP, а system устраняет необходимость вводить IP вручную.

Поля проходят весь путь: Builder → ссылка → разбор подписки → её собственные настройки → снимок сессии → native policy. Недостаточно сохранить их в форме. Изменения одиночного DNS, режима auto и default timeout тоже должны экспортировать аварийный резерв и bootstrap. Повторное обновление подписки сохраняет личные дополнения и явно заданные локальные overrides.

Для UI сохраняется существующая структура: под каждой DNS группой выбор аварийного резерва, отдельно общий bootstrap. Варианты: системный DNS, presets, собственный сервер, отключение резерва. В presets разделяются российские и глобальные службы, протокол и фильтрация. Базовый набор: Яндекс, SkyDNS, Google, Cloudflare, Quad9, AdGuard; доступность проверяется в сети пользователя, географическая группа не является гарантией работы. Частные DoH остаются поддерживаемыми. Новый крупный redesign не нужен.

Системные запросы привязываются к явно выбранной NOT_VPN сети. Предпочтителен ограниченный по времени и числу запросов Android resolver bridge с отменой, защитой локального интерфейса и проверкой поколения сети. На Android 29+ доступен DnsResolver с Network/CancellationSignal; для 26–28 требуется отдельный совместимый путь и тесты. Простое копирование LinkProperties DNS с сырыми UDP запросами не эквивалентно Android Private DNS.

Реализация bridge планируется через локальный Unix socket со случайным именем и проверкой UID вызывающего процесса. Не открывать незащищённый TCP/UDP DNS для других приложений. Сеть должна приходить от общего контроллера underlying network, согласованного с `HevVpnService`, а не выбираться как первый элемент `allNetworks`. Нельзя обращаться к default network без проверки NOT_VPN: она может быть самим VPN.

Нужно связать оба запуска: внешний `XrayService` (правила/DNS сайтов) и профильный `CoreService` (включая bootstrap адреса VPN сервера). Затем проверить изолированные URL-test пути Snell/других профилей. Для Android 26–28 `Network.getAllByName` не предоставляет тех же гарантий отмены и различения ошибок, что raw DNS API; ограниченный пул потоков и явная обработка этого ограничения обязательны. Проверка только современного планшета не заменит API 26–28 acceptance.

Изменение Xray adaptive DNS требует пересборки overlay и native бинарника. Экспериментальный sing-box router проверяется отдельно; нормальные профили Snell/Naive используют общий Xray router, поэтому название транспортного ядра не определяет владельца DNS. Поддержка не объявляется готовой по одной Kotlin форме.

## Последовательность проверок на устройстве

1. Сохранить сведения о версии/подписи и обезличенную эффективную DNS-конфигурацию. Снять baseline на уже выбранном профиле без изменения subscription data. Если нужны другие DNS, использовать временный тестовый источник/профиль с отдельным именем, а не переписывать личную подписку.
2. Независимое тестовое Android приложение делает свежие A/AAAA запросы через TUN. Запрос из процесса TUNA, исключённого из собственного VPN, не является такой проверкой. Собственный браузерный DoH проверяется отдельно.
3. Одиночный выбранный резолвер → 6/2 → 8/8; auto и priority. Для каждой проверки сохранить конфигурацию, поколение подключения, DNS telemetry и результат независимого запроса. Не считать отсутствие каждого провайдера в IPLeak ошибкой автоматического выбора.
4. Управляемые недоступные endpoints только в синтетической конфигурации: отказ одного, отказ всех, system reserve, custom reserve и disabled. При доступном основном сервере счётчик emergency должен быть нулевым; negative response и cancellation не должны вызывать reserve.
5. Изменение DNS/профиля и остановка во время запроса: старый callback не меняет новый статус, локальный bridge не остаётся после остановки, timeout не умножается на число DNS. Wi-Fi не выключается.
6. Пройти VLESS, Snell, Mieru, NaiveProxy на доступных рабочих профилях. Raw Xray JSON остаётся явным исключением, а изолированные URL-tests проверяются на тот же bootstrap, что обычный запуск.
7. Android 26–28: отдельный эмулятор/устройство для fallback API. Если доступен только планшет API 36, этот пункт отмечается непроверенным, а не автоматически пройденным.
8. После миграций безопасности повторить импорт/обновление подписки, локальные дополнения, обычный запуск и обновление APK поверх 1.5. Только затем финальные APK/EXE и контрольные суммы.

## Закрытие issue 2

Updater в текущей 1.5 отключён PRIVATE_DISTRIBUTION; системный установщик не делает установку незаметно и сам проверяет совместимость подписи обновления. Тем не менее до включения updater нужно:

- Исправить источник релизов, ограничить размер/время загрузки и разрешённые HTTPS перенаправления.
- Скачать во внутренний временный файл с одновременным SHA-256, проверить полный APK и только затем разрешить передачу установщику.
- Криптографически проверить APK, package ID, signer/допустимую lineage, versionCode и ABI. Одного извлечения сертификата PackageManager недостаточно для собственной полной проверки.
- Не считать checksum с той же страницы независимой аутентификацией. Основа доверия — ожидаемая подпись; при отдельном подписанном манифесте закрепить его ключ.
- Сузить FileProvider до каталогов реально выдаваемых файлов после проверки экспорта диагностики/резервных копий. Предотвратить подмену файла между проверкой и установкой.

Критерий закрытия: валидное обновление той же подписи проходит; чужая подпись/пакет, повреждение, обрыв загрузки и downgrade отвергаются до интента установки. Данные сохраняются. Updater остаётся выключенным до этих проверок.

## Закрытие issue 3

Составить перечень секретов и их копий: profiles JSON, активные native config, SOCKS пароли, subscription tokens, журналы, экспорт и backup. Android sandbox уже защищает внутренние файлы от обычных приложений; требуемое усиление — шифрование данных ключом Android Keystore, а не обещание защиты от полностью скомпрометированной ОС.

Шифрование AES-GCM с уникальным nonce и версионированным форматом. Миграция идемпотентная и атомарная: запись зашифрованной копии, проверка чтения, commit, удаление старой копии. При сбое ключа или миграции не очищать профили. Нельзя требовать биометрию для каждого автоматического запуска VPN.

Native plaintext файлы, если необходимы API ядра, хранятся только во внутреннем закрытом каталоге на минимальный необходимый срок. Очистка привязана к владельцу сессии, не мешает восстановлению другого процесса. Проверяются исключения cloud/device-transfer backup, аварийное завершение и экспорт без секретов. Гарантированное физическое стирание flash не обещается.

HTTP проверяется по всем загрузчикам и каждому redirect: публичные управляющие загрузки только HTTPS; явно разрешённый локальный HTTP не должен превращаться в переход на публичный HTTP. Динамические LAN адреса нельзя выразить одним статическим allowlist XML. Перед запретом глобального cleartext нужен совместимый ограниченный путь для LAN; передача обычного HTTP трафика пользователя через VPN от этого не блокируется. Native сетевые реализации проверяются отдельно от Android Network Security Config.

Критерий закрытия: обновление с 1.5, перезапуск/обрыв миграции, запуск VPN, импорт/refresh и backup проходят без потерь; секреты не остаются в постоянных plaintext хранилищах вне документированных runtime файлов; HTTP downgrade отвергается.

## Закрытие issue 4

Это замечание о локальном fingerprint, не подтверждённое удалённое исполнение или DNS leak. Убирается специфическая фиксированная пара адресов через отдельную политику выбора валидной TUN подсети с проверкой конфликтов LAN, MAPDNS и IPv6. Не брать интерфейсные адреса из произвольного proxy профиля и не вводить постоянный уникальный per-install идентификатор под видом анонимности.

MTU не рандомизируется и не меняется в security исправлении. Локальный SOCKS остаётся loopback с аутентификацией; SO_PEERCRED относится к Unix sockets, его нельзя механически перенести на TCP порт. Критерий закрытия: адреса и маршруты корректны при перезапуске/смене сети, IPv4/IPv6 и MAPDNS работают, чужое приложение не проходит SOCKS authentication. Сам факт Android VPN остаётся обнаружимым.

## Приёмка и выпуск

- DNS unit/native: 1, 6/2 и 8/8; auto/priority; A/AAAA; UDP/TCP/DoH; отказ одного/всех; terminal reserve; NXDOMAIN; cancellation; восстановление; общий deadline; отсутствие раннего системного запроса.
- Контракт: standalone import и subscription refresh, сохранение/перезапуск/export, bootstrap и оба резерва, неизвестные поля/версии, конфликтующие routes и личные overrides.
- Android TUN: VLESS, Snell, Mieru, Naive при доступных профилях; отдельное приложение делает свежие запросы; browser DoH исключён из трактовки. Транспортный SOCKS тест не заменяет TUN проверку.
- Жизненный цикл: потеря/возврат доступной сети без выключения Wi-Fi при беспроводной отладке, переподключение, смена DNS, отмена старого запуска, отсутствие постоянных wake locks и бесконечных фоновых проб.
- Security: независимый attacker test app, негативные APK fixtures, прерывание миграции, экспорт/backup/логи, HTTP redirects.
- Релиз: новый production signer с доказанной signing lineage, неизменный package ID, увеличенный versionCode, установка поверх 1.5 без удаления данных, актуальные native provenance, APK/однофайловый Builder EXE, SHA-256 и отчёт с непроверенными сценариями. ## Новый релизный ключ без удаления старой установки

Проверен локальный опубликованный APK 1.5: APK Signature Scheme v2, `CN=Android Debug`, SHA-256 сертификата `c3c08cdde6a991b036a5b14f07680116355ac8b8e0eadf44144d82e7c514131b`. V3/v3.1 отсутствуют. Это действительно исторический debug сертификат, хотя APK собран как release и не debuggable. Переименование keystore или строки Subject не превращает его в новый доверенный release signer.

Новая подпись требует signing certificate lineage — криптографического разрешения перехода от старого ключа к новому. Нужны оба закрытых ключа; наличие старого APK или публичного сертификата не заменяет старый private key. Локальный debug keystore существует, но соответствие/доступность его ключа ещё не проверены. Ничего с ключами в этапе планирования не менялось.

1. Сверить сертификаты установленной версии, опубликованного APK и имеющегося старого ключа. Проверить, нет ли распространявшихся APK с другим signer. Разные старые ключи нельзя объединить в одну lineage.
2. Создать отдельный production keystore вне публичного дерева, с надёжным секретом и резервной копией. Не передавать пароли в аргументах команд, логи или Git. Не заменять старый keystore: он нужен для подтверждения перехода и выбранной совместимости.
3. Создать lineage старый → новый с помощью SDK `apksigner rotate`. Сохранить публичную lineage и контрольную сумму; приватные ключи хранить отдельно. Не давать старому signer право подписывать произвольные будущие откаты без отдельной необходимости.
4. Собрать release с прежним application ID, повышенным versionCode и `debuggable=false`. ZIP alignment выполняется до финальной подписи. Проверить все схемы и ожидаемый signer для каждого диапазона API, а не только один SHA в сводном выводе.
5. Updater из issue 2 должен криптографически проверять lineage/актуальный signer, а не принимать любое совпадение с историей сертификатов. Не разрешать APK только со старым signer после успешной ротации или произвольный новый сертификат без доказательства перехода.
6. На планшете обновить настоящую установленную 1.5 без uninstall/clear data. Проверить UID, профиль/подписку/настройки, Android Keystore, VPN permission, запуск и подпись по PackageManager. Затем проверить последующее обновление тем же новым ключом и отказ APK без корректной lineage на отдельной тестовой установке.

### Политика старых Android — выбор владельца зафиксирован

Минимальная версия приложения сейчас Android 8 / API 26. Ротация поддерживается с Android 9, но документация AOSP не рекомендует её на Android 12 и старше из-за исторических ограничений. Стандартный современный вариант — v3.1 с ротацией с Android 13 / API 33. Тестовый планшет API 36 подходит для него.

**Владелец выбрал первый вариант:** сохраняем Android 8–12, используем новый release signer с Android 13+, прежнюю подпись — только для совместимости старых ОС. MinSdk остаётся 26, rotation minimum — 33. Альтернативы ниже сохранены только для объяснения ограничения, не являются текущим заданием.

| Вариант | Android 13+ | Android 9–12 | Android 8 |
| --- | --- | --- | --- |
| Сохранить совместимость, рекомендованный baseline | Новый release signer + lineage | Прежний signer в совместимой схеме | Прежний signer v2 |
| Только новый signer, минимальный Android 13 | Новый release signer + lineage | Остаётся предыдущая версия | Остаётся предыдущая версия |
| Ротация с Android 9, расширенный стенд | Новый release signer + lineage | Новый signer v3, отдельные проверки известных ограничений | Остаётся предыдущая версия либо отдельно согласованный legacy APK |

Одновременно убрать старый сертификат полностью и сохранить бесшовное обновление на Android 8 невозможно. В первом варианте старый сертификат остаётся намеренно для старых ОС; нельзя описывать такой универсальный APK как «вообще без debug подписи». Наличие старого сертификата в самой lineage также нормально: оно доказывает переход, а не делает новый signer debug.

MinSdk не повышается. На миграцию планируется часть заключительных 8 пунктов бюджета. Матрица подписи: API 26/27 и 28–32 принимают прежний signer; API 33+ принимает новый signer с lineage. На планшете проверяется реальное обновление, на старых API — проверка SDK и по возможности отдельный emulator/device install; граница доказательства указывается в отчёте. До проверки ротации не устанавливать случайно подписанный production APK поверх основной установки.
